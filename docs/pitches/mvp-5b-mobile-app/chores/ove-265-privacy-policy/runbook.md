**Audit facts behind the policy** (Production, 2026-11-26):

- **Not used:** analytics, advertising, tracking, or crash-reporting SDKs (web and mobile `package.json`), third-party script tags, location, contacts, camera, microphone, health data, and push notifications.
- **Photos:** read only through the system picker. The phone re-encodes the image to a JPEG, which strips EXIF data.
- **Cookies and storage:** the Supabase auth cookies, plus `localStorage` and `sessionStorage` for interface preferences and the checkout return.
- **Production environment:** `app-config` reports `planImportEnabled: false`. There is no `ANTHROPIC_API_KEY` and no `TRIAL_DEDUPE_ENABLED`. Stripe and Turnstile are configured. The support address is `support@overloadtraining.app` (`NEXT_PUBLIC_OVERLOAD_SUPPORT_EMAIL`, served by `/support` and `app-config`).
- **Deletion:** `src/lib/accounts/deletion.ts` cancels Stripe subscriptions first. Then it deletes every owned model in one transaction, removes Storage objects best-effort, and removes the auth identity.
- **What survives deletion:**
  - `admin_audit_entries`: the former account id and the action, with no name or email. That id is also in the Stripe customer's metadata.
  - `auth_throttle`: unsalted SHA-256 keys of the IP address (or the browser details) or of the account id. Sign-up and reset rows are never pruned. The page says this plainly. Keying the hash with a server secret and pruning old rows would be a later hardening chore, not part of this one.
  - `webhook_events`: Stripe event ids.
  - Supabase Auth's own audit log: IP and user agent, kept under Supabase's retention.
  - Vercel logs.
  - Backups.
  - Stripe.
- **Server logs** never include names, emails, or training content (CLAUDE.md rule).

## 4. The iPhone app: does build 1.0.0 (1) have the link?

**No.** The installed TestFlight build 1.0.0 (1) was built before this change and has no privacy link.

**The change is JavaScript only.** It adds no native module and doesn't change `app.config.ts` or anything it loads. With identical commands, the Production fingerprint was the same with and without the change, and `fingerprint-inputs.test.ts` keeps the staging runtime at `2e4a65d9…`. So both delivery paths below work.

- **A. Over-the-air update to 1.0.0 (1) (no new build).** After the release merges, run the guarded Production update from a clean `main`: `npm run mobile:update:production`. Build 1.0.0 (1) downloads it on launch and shows it on the **next** launch. Check it: open the app twice, then More → Your data → Privacy Policy.
- **B. New build 1.0.0 (2) from `main` (recommended for the Beta App Review submission).** It has the link on first launch, so Apple's reviewer sees it even if they open the app only once: `npx eas-cli build --platform ios --profile production --auto-submit` from a clean `main` after the release merges. Submit build (2) to the Friends group instead of build (1).

You can do both. A is enough for testers who already installed build (1).

## 5. Releasing to Production (owner)

1. Read the policy on the staging URL and check §2. If anything changes, ask the run for the edit. Every change goes through staging first.
2. Merge the release PR into `main` (it is open and not merged). It has only this chore. It doesn't carry the "Overload on iPhone" note (release B) and doesn't change `MOBILE_TOUR_AUTO_START`.
3. Once Vercel shows the Production deployment as Ready, check from a private window or `curl`:
   - `curl -sI https://www.overloadtraining.app/privacy` → `200`, no redirect to `/login`.
   - The footer on `https://www.overloadtraining.app/` shows Privacy Policy.
   - `https://www.overloadtraining.app/sitemap.xml` lists `/privacy`.
4. Enter the URL in App Store Connect (§3).
5. Deliver the app link (§4, A and/or B).
6. Tell the run "privacy released", and it syncs `main` back into `staging`.
